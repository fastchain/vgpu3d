# 🎮 vgpu3d

### Hardware 3D for Windows VMs on QEMU/KVM, on the GPU your host already has

**Vulkan · Direct3D 9 / 10 / 11 / 12 · OpenGL 4.6 · OpenCL 3.0** for Windows 11 guests over `virtio-gpu` (Venus).<br>
No GPU passthrough, no second card, no vGPU licenses. The host keeps its desktop.

## 💡 When it's useful

`vgpu3d` is a WDDM driver for the Windows 11 guest. It forwards the guest's graphics work to the
**host's own Vulkan driver** through QEMU's `virtio-gpu` device. The VM gets real GPU acceleration
while the GPU stays shared with the host and with other VMs.

| ✅ Good fit | ❌ Look elsewhere |
|---|---|
| CAD and 3D tools in a Windows VM (Autodesk Fusion: **~60 fps instead of 1.4 fps** on CPU) | Competitive gaming at native-GPU frame rates: use GPU passthrough (VFIO) |
| A smooth, GPU-composited Windows desktop on a Linux workstation | Games with kernel anti-cheat (they usually block VMs anyway) |
| Lighter and older games, emulators, GPU-accelerated apps | CUDA workloads (NVIDIA-only, not possible here) |
| Hosts with only one GPU, or consumer GPUs without SR-IOV | Production machines that need signed drivers and Secure Boot |
| Several Windows VMs sharing one card | |

**Compared with the usual options on KVM:**

| | **vgpu3d** | Display-only virtio / QXL | GPU passthrough (VFIO) | SR-IOV / NVIDIA vGPU |
|---|---|---|---|---|
| Host keeps using the GPU | ✅ | ✅ | ❌ dedicated to the VM | ✅ |
| Hardware needed | any Venus-capable Vulkan GPU | none | 2nd GPU + IOMMU | data-center GPU, licenses |
| Windows 3D / compute | Vulkan, D3D9–12, GL 4.6, OpenCL 3.0, DirectML | ❌ CPU only (WARP) | everything, native | everything, native |
| VMs per GPU | many | – | one | many |
| Speed | good; CPU-bound on light loads | very slow 3D | native | near native |

## 🧩 Supported APIs and engines

The guest sees one adapter, **"vgpu VirtIO GPU 3D (WDDM)"**, and reports the host GPU by name
(e.g. `Virtio-GPU Venus (NVIDIA GeForce RTX 4090)`) with the host GPU's memory as dedicated video memory.
Apps use it automatically, with no per-app setup.

| API | 64-bit | 32-bit | Implementation |
|---|:---:|:---:|---|
| **Vulkan 1.4** | ✅ | ✅ | Mesa **Venus** ICD → host Vulkan driver |
| **Direct3D 12** | ✅ | ✅ | Triton D3D12 DDI + **vkd3d-proton** (in-process) |
| **Direct3D 10 / 11** (FL 11_1) | ✅ | ✅ | Triton D3D10/11 DDI + **DXVK** (in-process) |
| **Direct3D 9** | ✅ | ✅ | Windows' **D3D9On12** on our D3D12 driver |
| **OpenGL 4.6** | ✅ | ✅ | Mesa **Zink** (OpenGL on Vulkan) |
| Desktop (DWM) | ✅ | – | GPU-composited through D3D11 |
| **OpenCL 3.0** | ✅ | ❌ | **clvk** (OpenCL on Vulkan, clspv compiler built in) |
| DirectML | ✅ | – | Windows' DirectML.dll on our D3D12 |

**Tested engines and apps:** 3DMark (Steel Nomad), Unigine (Heaven, Valley, Superposition), Tellusim (GravityMark),
FurMark 2, PassMark PerformanceTest, Autodesk Fusion, Steam client, plus the repository's own
D3D9/11/12, Vulkan and OpenGL test programs. Display modes go up to **5120×2160**.

## 🖥️ Prepare the host (step by step)

Full details, with every XML element explained: **[docs/SETUP.md](docs/SETUP.md)**.
Working domain template: **[docs/examples/WIN11_3D.xml](docs/examples/WIN11_3D.xml)**.

**1. Check the software.** You need QEMU ≥ 9.2, libvirt ≥ 9 and virglrenderer ≥ 1.0 built with Venus:

```sh
qemu-system-x86_64 -device virtio-vga-gl,help | grep -E 'blob|hostmem|venus'   # all three listed
ls /usr/libexec/virgl_render_server /usr/lib/*/virgl_render_server 2>/dev/null  # Venus render server
```

**2. Check the GPU.** The host Vulkan driver needs 1.3-class features plus dma-buf export
(NVIDIA proprietary is tested; AMD RADV and Intel ANV are Venus's main targets):

```sh
vulkaninfo | grep -E 'VK_EXT_external_memory_dma_buf|VK_EXT_image_drm_format_modifier|VK_KHR_external_memory_fd'
```

**3. Let QEMU start the Venus render server.** In `/etc/libvirt/qemu.conf`:

```ini
seccomp_sandbox = 0
```

```sh
sudo systemctl restart libvirtd
```

**4. Give QEMU the render node:**

```sh
sudo usermod -aG render libvirt-qemu      # "qemu" on Fedora/Arch
ls -l /dev/dri/by-path/                   # pick the renderD* of the GPU to use
```

**5. Configure the VM** (start from `docs/examples/WIN11_3D.xml`). The parts that matter:

```xml
<domain type="kvm" xmlns:qemu="http://libvirt.org/schemas/domain/qemu/1.0">
  <memoryBacking><source type="memfd"/><access mode="shared"/></memoryBacking>
  <os firmware="efi">
    <firmware>
      <feature enabled="no"  name="enrolled-keys"/>   <!-- Secure Boot capable, not enforced -->
      <feature enabled="yes" name="secure-boot"/>
    </firmware>
  </os>
  <devices>
    <graphics type="spice" autoport="yes"><listen type="address" address="127.0.0.1"/></graphics>
    <graphics type="egl-headless"><gl rendernode="/dev/dri/renderD128"/></graphics>
    <video><model type="virtio" heads="1" primary="yes"><acceleration accel3d="yes"/></model></video>
  </devices>
  <qemu:commandline>
    <qemu:arg value="-global"/><qemu:arg value="virtio-vga-gl.blob=true"/>
    <qemu:arg value="-global"/><qemu:arg value="virtio-vga-gl.hostmem=4G"/>
    <qemu:arg value="-global"/><qemu:arg value="virtio-vga-gl.venus=true"/>
  </qemu:commandline>
</domain>
```

**6. Start it:**

```sh
sudo virsh define WIN11_3D.xml && sudo virsh start WIN11_3D
sudo tail -f /var/log/libvirt/qemu/WIN11_3D.log     # no "failed to initialize venus renderer"
```

## 🪟 Install on the guest (step by step)

**Requirements:** Windows 11 x64, Secure Boot **not enforced** (the driver is test-signed),
about 200 MB of free disk space.

**Turn off Fast Startup / hibernation** in the guest (elevated prompt: `powercfg /hibernate off`). Fast Startup
resumes the guest's graphics driver state from disk, while QEMU and virglrenderer start fresh: host resources
the restored driver expects are gone, and allocations fail after such a "shutdown". Use full shutdowns and restarts.

### With the installer (recommended)

1. **Copy** `vgpu3d-setup-<version>.exe` into the VM.
2. **Save your work.** The display adapter restarts during installation, and apps holding the GPU may close.
3. **Run it** and accept the UAC prompt. Setup checks for Windows 11 x64 and the virtio-gpu adapter, then:
   - turns on **test signing** if it's off. Reboot when asked; installation **continues
     automatically** at the next logon;
   - creates a local code-signing certificate and trusts it;
   - signs the driver, builds its catalog and installs it with `pnputil`.
4. **Reboot if the finish page asks** (usually needed only when switching away from Basic Display).
5. **Check:** Device Manager → Display adapters shows **vgpu VirtIO GPU 3D (WDDM)**, status OK.
   The desktop shows a "Test Mode" watermark.

Silent install: `vgpu3d-setup-<version>.exe /S` (exit code 3010 = reboot needed).
**Uninstall:** *Settings → Apps → Installed apps → vgpu3d virtio-gpu 3D driver*. This removes the driver
(the adapter falls back to Microsoft Basic Display) and the certificate. To turn test signing back
off: `bcdedit /set testsigning off`.

### Manually (from the zip)

```powershell
# elevated PowerShell, inside the unpacked vgpu3d-m1.zip
bcdedit /set testsigning on        # once, then reboot (install.ps1 also offers this)
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

### Verify

| Check | Expected |
|---|---|
| `vulkaninfo --summary` | `Virtio-GPU Venus (<host GPU>)` |
| `dxdiag` → Display | vgpu adapter, Direct3D acceleration enabled |
| any OpenGL app | renderer `zink Vulkan 1.4(Virtio-GPU Venus (<host GPU>))` |

## ⚙️ How it works

```
 Windows guest                                              Linux host
 ┌───────────────────────────────────────────────┐          ┌───────────────────────────────┐
 │ D3D12 app ─► vgpu UMD (Triton DDI+vkd3d-proton)┼─┐        │ QEMU virtio-vga-gl            │
 │ D3D9 app  ─► D3D9On12 ─► D3D12 path above      │ │        │   (blob, hostmem, venus)      │
 │ D3D10/11  ─► vgpu UMD (Triton DDI + DXVK) ─────┼─┤        │                               │
 │ OpenGL    ─► opengl32 ─► Mesa Zink ────────────┼─┤        │ virgl_render_server           │
 │ Vulkan    ─► vulkan-1 ─────────────────────────┼─┤ rings  │ (Venus decoder)               │
 │                         ▼                      │ └───────►│        ▼                      │
 │              Mesa Venus ICD (vulkan_virtio)    │          │ host Vulkan driver            │
 │                         │ D3DKMT               │ virtio   │ (NVIDIA / AMD / Intel)        │
 │              viogpu3d.sys (WDDM 2, GpuMmu) ────┼─────────►│        ▼ host GPU             │
 └───────────────────────────────────────────────┘          └───────────────────────────────┘
```

- **`viogpu3d.sys`**: a WDDM 2 render and display miniport (GPU virtual memory, monitored fences,
  residency, mode setting), derived from the virtio-win viogpu3d line.
- **Venus**: Mesa's Vulkan-over-virtio driver with a new Windows backend (D3DKMT contexts, shared memory,
  cross-process sharing). Everything else is built on top of it.
- **D3D10/11/12**: a WDDM user-mode driver running DXVK and vkd3d-proton **in-process** behind Triton's DDI layer.
- **OpenGL**: Mesa Zink, registered as the system OpenGL ICD.
- **32-bit apps**: a complete WOW64 set of the user-mode parts on the same kernel driver.
- **Display**: frames reach QEMU through a framebuffer copy, which works on every host, including NVIDIA with egl-headless.

Progress log and design notes: [docs/STATUS.md](docs/STATUS.md).

## ⚠️ Limitations

- **Test-signed:** needs test signing, so Secure Boot must be off (not enforced).
- **OpenCL is 64-bit only** (clvk). Do **not** install Microsoft's *OpenCL, OpenGL and Vulkan Compatibility
  Pack*: its Dozen driver and our D3D12 driver call each other, and every Vulkan app deadlocks.
- **No CUDA**: it needs NVIDIA's own driver and hardware in the guest.
- **Driver install/update restarts the adapter.** Apps using the GPU (Explorer, DWM) restart.
- Light workloads are CPU-bound, and the desktop costs CPU at very high resolutions.
- Tested on NVIDIA (RTX 4090) only; AMD and Intel hosts are expected to work but are untested.

Full list and troubleshooting: [docs/SETUP.md §8–9](docs/SETUP.md#8-known-limitations).

## 🎞️ Tearing and picture artifacts

Frames travel app → Windows' compositor (DWM) → the driver's framebuffer copy → host (QEMU egl-headless) →
SPICE → viewer. What we know about artifacts along that path (measured with the
[`src/umd/tearcheck`](src/umd/tearcheck) programs, which alternate solid red and blue frames and check
what DWM shows and what the driver hands to the host):

| Where | Status |
|---|---|
| Guest framebuffer → host | **Fixed** in 1.0.26313.7767: the next frame overwrote the framebuffer while the host was still reading the previous one (up to ~3 % of frames in fast motion). |
| Modern apps (flip-model D3D11/D3D12: most games, 3DMark, Unigine) | **Clean**: 0 mixed frames, windowed, borderless and exclusive fullscreen. |
| Older windowed D3D apps (legacy *blt-model* swap chains) running **uncapped** | **Mostly fixed** in 1.0.26313.7767: ~1–2 % of frames mixed (was ~17 %). The copy into DWM's window surface could overlap DWM reading it on the host GPU, because DWM composes outside Windows' GPU scheduler; it now waits while DWM composes, which lowers such apps' *uncapped* frame rate (test window ~400 → ~120 fps). Clean with vsync on. |
| Vulkan and OpenGL apps in a window (e.g. GravityMark-Vulkan, FurMark) | **Fixed** (next release): they used to end with a GDI blit into the window, which tore in 1–5 % of frames. They now present through a flip-model DXGI swap chain: 0 mixed frames, ~4 % lower GravityMark score. `VGPU_WSI_DXGI=0` (environment) or `HKLM\SOFTWARE\vgpu` `WsiDxgi`=0 (DWORD) restores the GDI path. |
| Host side (QEMU readback, SPICE, viewer) | Not measurable from the guest. Steel Nomad's frames leave the guest clean, yet patches can show in fast motion in virt-manager's console; turning SPICE streaming and image compression off did not change it. |

**What helps today**

- Turn **vsync** on in apps that offer it (blt-model apps are then clean).
- Prefer fullscreen or borderless modes of modern (flip-model) apps.
- If patches show in fast motion, try another viewer, e.g. `remote-viewer spice://127.0.0.1:5900`
  instead of virt-manager's built-in console.

The driver cannot see exactly when DWM starts reading a window, so the blt-model fix waits conservatively
(from each vsync until DWM's frame is done): hence the residual ~1–2 % and the frame-rate cost for uncapped
blt-model apps. Details: [docs/STATUS.md](docs/STATUS.md).

## 🔨 Building from source

Everything cross-compiles on Linux: MinGW-w64 (posix), clang/lld (clang-cl for the kernel driver),
meson and ninja, plus the WDK/SDK headers in `toolchain/`. NSIS (`makensis`) is needed for the installer.

```sh
build/package_kmd3d.sh release     # kernel driver + 64/32-bit UMDs, Venus, Zink -> out/vgpu3d-m1.zip
build/build_installer.sh           # NSIS installer -> out/vgpu3d-setup-<version>.exe
build/build_installer.sh --package # both in one go
```

The individual builds are `build_kmd3d.sh`, `build_umd.sh [32]`, `build_dxvk.sh [32]`,
`build_vkd3d.sh [32]`, `build_triton_venus.sh [32]` and `build_gl.sh [32]`. OpenCL: `build_clvk.sh` (clvk with an
LLVM/clspv cross-build, ~10 min on 32 cores) and `build_opencl_loader.sh [32]` (Khronos `OpenCL.dll`).

| Path | Contents |
|---|---|
| `src/kmd3d/viogpu/` | WDDM kernel driver; `src/kmd3d-inf/` has the INF and Vulkan ICD manifests |
| `src/umd3d/` | D3D10/11/12 user-mode driver backend (Triton DDI → DXVK / vkd3d-proton) |
| `src/installer/` | NSIS installer script |
| `src/umd/` | guest test programs (`d3d9test`, `d3d11test`, `d3d12test`, `blttest`, `gltest`, `vkcompute`, …) |
| `patches/` | our changes to Mesa, Triton, DXVK, vkd3d-proton and clvk |
| `build/` | cross-build, packaging and installer scripts |
| `tools/windows/` | guest scripts: install/uninstall, test rounds, benchmark runners |
| `docs/` | setup manual, progress log, design notes |
